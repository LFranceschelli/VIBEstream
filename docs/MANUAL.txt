  --------------------------------------------------------------------------
  IF THE CAMERA WORKED BEFORE AND NOW GIVES A WINDOWS DLL DIALOG
  --------------------------------------------------------------------------
  Symptom: a modal Windows box saying the procedure entry point could not be
  found in  ...\Prophesee\lib\metavision\hal\plugins\hal_plugin_prophesee.dll

  This is NOT "the camera is unplugged".  With the SDK healthy and no camera
  connected you get a clean console line instead:

      No devices found. Check connection and MV_HAL_PLUGIN_PATH.

  The dialog appears at DeviceDiscovery.list(), i.e. when HAL enumerates its
  plugins - before it looks for hardware.  The HAL plugins are C++ DLLs; which
  dependencies they resolve to depends on PATH.  So the SAME code opens the
  camera under one interpreter and fails under another.  Anaconda is the usual
  culprit: its Library\bin shadows Prophesee's own dependencies.

  Diagnosis, one command, run it from the place where the camera DOES work:

      python tools/check_env.py

  Run it again from the interpreter VibeStream.bat prints at startup.  If the
  "executable" lines differ, paste the working one into PYTHON_EXE at the top
  of VibeStream.bat (or put the conda environment name in CONDA_ENV - a conda
  env must be ACTIVATED, not just have its python.exe called, because
  activation is what fixes PATH, and PATH is the whole problem).

  VibeStream.bat prints the interpreter, the package check and the metavision
  import result before it starts, so this is visible at a glance.

--------------------------------------------------------------------------------
  KEYBOARD REFERENCE   (press these on the "EBIV Live Stream" window)
--------------------------------------------------------------------------------

  ALWAYS AVAILABLE
    q     quit; the pump is driven to the safe voltage on the way out
    p     RT-EBIV on/off (the vectors).  OFF while a controller runs makes the
          measurement go stale: the supervisor will HOLD, then go SAFE
    v     Westerweel-Scarano validation on/off
    d     double exposure: overlay the previous frame on the current one
    b     blackout: hide the image, show only the vectors
    s     start/stop recording a .raw file
    w     start/stop saving .tif frames
    f     start/stop saving RT-PIV fields as .mat
    g     strip chart on/off (target, filtered, raw, pump voltage vs time)
    u     CROSS-STREAM PROFILE on/off  -- see below
    U     restart the profile averaging (shift+u)

  ONLY IN A CONTROL MODE  ('manual', 'calibration', 'closed_loop')
    +/-   loop OPEN   : move the pump voltage by CAL_MANUAL_STEP_V
          loop CLOSED : move the TARGET by REF_LIVE_STEP, if the reference
                        kind is 'live'; otherwise they do nothing and say so
    c     arm / disarm the closed loop (bumpless both ways)
    t     snap the live target onto the current measured velocity.  Press [t]
          then [c] and the loop closes with zero initial error
    0     set the pump to SAFE_PUMP_VOLTAGE and return to MANUAL
    x     EMERGENCY: force the SAFE state immediately

  In STREAM_MODE = 'ebiv' the six control keys do nothing, and say so: that
  mode creates no pump object and no control thread.

  THE CROSS-STREAM PROFILE  [u]
    Plots the feedback component across the WHOLE DisplayROI, averaged along
    the stream and smoothed over frames, with the ControlROI marked on it.
    Use it to put the ControlROI on the potential core rather than across the
    shear layers.  The footer reports the ControlROI mean and the spread
    across it; above 15% of the mean it warns, because a mean taken over a
    steep part of the profile moves when the jet flaps and when the ROI is a
    few pixels off.

    For '-u' or 'u' (a horizontal jet) the profile runs down the rows; for
    'v' or '-v' it runs across the columns.

--------------------------------------------------------------------------------
  0. READ THIS FIRST
--------------------------------------------------------------------------------

  * The WaveForms desktop application holds an EXCLUSIVE lock on the Analog
    Discovery.  Release 5.0 opens the device from Python, so WaveForms must be
    CLOSED.  Because Python then owns the device, Release 5.0 also generates
    the laser waveform.  Transcribe your GUI settings into the LASER_*
    parameters in EBIV_Main.py, or there will be no laser.

  * Run FLAG_VERIFY_HARDWARE once, with an oscilloscope on the laser output,
    before trusting any closed-loop result (§8).

  * Run RUN_MODE='calibration' before choosing PID gains (§6.3).  There is no
    voltage-to-velocity relation hard-coded anywhere in this software, and you
    should not assume one is linear.

  * SAFE_PUMP_VOLTAGE defaults to 0.0 V.  Decide for your facility whether
    stopping the pump is actually the right thing to do when the controller
    loses sight of the flow; holding a low but non-zero flow is often better.

  * The controller never arms itself.  'closed_loop' starts in MANUAL; you
    press [c].

  1b. THE PARAMETER WINDOW  (new in Release 5.1)
--------------------------------------------------------------------------------

    VibeStream.bat               double-click; always opens the window
    python EBIV_Main.py --gui    the same thing from a prompt
    python EBIV_Main.py          obey the flags in the file instead

Editing EBIV_Main.py by hand still works exactly as before: set FLAG_GUI to
False and everything behaves like Release 5.0.

  1.  Choose what to run, at the top of the window:

        Live streaming    the camera path, with the streaming sub-mode next
                          to it: ebiv / manual / calibration / closed_loop.
        Offline chain     record .raw, play back, generate frames, offline
                          PIV.  Tick any subset; they run in that order, in
                          one go.

      The tabs follow the choice: the offline chain hides the controller,
      hardware and calibration tabs, and the streaming sub-mode is disabled.

  2.  Edit the parameters on the tabs.  110 parameters are exposed; hovering
      a label shows what it does and what it costs.  The tabs are

        Run           output folders, acquisition name, raw file, profiler
        Acquisition   f_acq, contrast clamp, trigger, image flips, biases
        PIV & ROIs    window, node distance, workers, sub-pixel, validation,
                      DisplayROI and ControlROI
        Offline       frame generation and pyramid levels  (offline only)
        Feedback      streamwise component, validity gates, px/mm units
        Controller    filter, reference trajectory, PID, rates, safe state
        Hardware      Analog Discovery: laser and pump channels
        Calibration   the open-loop voltage programme, and logging
        Display       refresh rates, arrow decimation, strip chart
        Log           everything the last run printed; save it to a file

  3.  Validate, then Run.

Presets.  Save preset... / Load preset... write the whole configuration as
JSON, so one file describes one experiment completely.  The current settings
are also written to VibeStream_last_settings.json (next to EBIV_Main.py) when
you press Run, and restored the next time the window opens, so you do not have to re-enter anything.  A
preset written by a different version still loads: unknown entries are
ignored and listed rather than refused.

Validation.  Validate (and Run) check the acquisition parameters, the
control-system cross-checks, ControlROI containment, the pump voltage limits
and the reference file, and report every problem at once.  Starting a closed
loop with the Analog Discovery enabled asks for confirmation first.

What the window does NOT do yet.  While a run is in progress the window is
hidden and the pipeline owns the process: the live stream opens its own
OpenCV windows, and the offline steps print to the console.  The window
returns when the run ends, with the whole log on the Log tab.  A live log and
a Stop button need the pipeline on a worker thread, which takes care because
OpenCV HighGUI and matplotlib both want the main thread — that is a 5.2 item,
not an oversight.

Adding a parameter.  Add the field to the dataclass in ebiv_config.py and one
line to PARAM_SPEC in ebiv_gui.py.  There is no second copy of the parameter
list, and the test-suite fails if a spec entry points at nothing or if a
config field is neither exposed nor listed in INTENTIONALLY_HIDDEN — so a new
field cannot quietly become unreachable from the GUI.


--------------------------------------------------------------------------------
  2. ARCHITECTURE AND CONTROL DATA FLOW
--------------------------------------------------------------------------------

    event camera
        |  EventsIterator(delta_t = accum_time_us)
        v
    ACQUISITION THREAD (main)
        event accumulation  ->  pseudo-frame (uint8)
        crop to DisplayROI
        piv_queue.put((frames, t_frame, validate))     Queue(maxsize=1)
        ... also owns every OpenCV window; HighGUI is not thread-safe
        |
        v
    PIV WORKER THREAD                            runs as fast as it can
        CPUCorrelator.correlate()   ->  U, V, CC
        universal_outlier_detection ->  cleaned field + validity mask
        FieldHolder.publish(...)                 for the display
        ControlROIEstimator.estimate(U, V, mask, CC)
              raw U,V + mask, so rejected vectors are EXCLUDED, not
              replaced by a local median
        MeasurementHolder.publish(Measurement(...))   one atomic assignment
        |
        v
    CONTROL THREAD                               control_rate_hz, independent
        m = MeasurementHolder.read()
        validity: valid flag, finite, fresh sequence, age < max_age
        TemporalFilter.update(u_raw, measured dt)     -> U_control_filtered
        ReferenceGenerator(t since arming)            -> U_target
        PIDController.update(target, filtered, measured dt)
        PumpBackend.set_voltage(V)                    -> AD3 W2, or MockPump
        ExperimentLogger.log_step(...)
        StripChart.append(...)                        deque append only
        |
        v
    Analog Discovery 3, Analog Out ch1 (W2)  ->  EcoDrift 4.3 0-10 V input

Three rates, all independent and all configurable:

    EBIV field rate          as fast as the correlator manages
    control_rate_hz          default 10 Hz
    visualization_rate_hz    default 20 Hz   (main image)
    plot_rate_hz             default  5 Hz   (strip chart)

Rendering can never determine control timing: the controller runs on its own
thread, and the strip chart only receives deque appends from it.

Every dt is MEASURED with time.perf_counter(), never assumed.  The control
thread advances its wake-up by exactly one period so jitter does not
accumulate into drift, and re-bases (rather than firing catch-up steps) if it
falls more than three periods behind.  The measured control interval and the
end-to-end latency are reported at the end of every run.

Threading rationale.  The expensive stage is one scipy FFT call that releases
the GIL, so a single PIV worker genuinely overlaps with acquisition.  More
Python-level PIV threads would not help.  Multiprocessing was considered and
rejected: shipping ~14 MB of window buffers per field across a pipe costs more
than the correlation.


--------------------------------------------------------------------------------
  3. THE TWO ROIs
--------------------------------------------------------------------------------

  DisplayROI   [x0, x1, y0, y1] in sensor pixels, or None for the full sensor.
               Where vectors are computed and drawn.  Release 4.0's
               `processing_roi`.

  ControlROI   [x0, x1, y0, y1] in sensor pixels.  Must be inside DisplayROI;
               this is checked at start-up and a violation is refused with a
               message naming both regions.  Only vectors here feed the
               controller.  It is drawn on the live image as a cyan rectangle
               with corner ticks, so what the controller is looking at is
               never in doubt.

Both are set independently in EBIV_Main.py §A.  Changing the ControlROI does
not change the DisplayROI or the vector field you see.

Grid nodes are selected once, at start-up, as a contiguous slice — not with a
per-frame boolean mask.  Node (gy,gx) has its window centre at
`display_roi[0] + gx*node_distance + window_size//2` (and likewise in y), so
the ControlROI must be at least one node spacing across in both directions;
if it selects no nodes, start-up fails with a message telling you the node
spacing.

Cropping the DisplayROI is the single biggest performance lever: correlation
cost scales with the number of interrogation windows.  A 900x400 ROI is about
a quarter of the work of a full 1280x720 frame.

IMAGE FLIP (FLAG_FLIP_X / FLAG_FLIP_Y), and how it interacts with the ROIs.

  Both flags are inherited from Release 4.0 and still work.  The flip is
  applied to the FULL sensor frame at frame construction, so it propagates
  consistently to the display, the RT-PIV, the .tif saving and the offline
  PIV — everything downstream sees the same mirrored image.

  Two consequences, both printed at start-up whenever a flip is active:

  1. The flip happens BEFORE the ROI crop, so DISPLAY_ROI and CONTROL_ROI are
     then in FLIPPED-image coordinates, not raw-sensor coordinates.  A
     rectangle at x = 200..1100 in the flipped image of a 1280 px sensor is
     x = 180..1080 on the sensor itself.  Start-up prints the equivalent
     raw-sensor rectangles for both ROIs so you can check them against what
     you see through the camera.

  2. flip_x negates U; flip_y negates V.

  IF YOUR ONLY PROBLEM IS THE SIGN — the jet runs right-to-left and the
  controller wants a positive streamwise component — DO NOT USE A FLIP.  Set

      CONTROL_COMPONENT = '-u'

  instead.  It costs nothing, leaves the ROI coordinates in the sensor's own
  frame, and leaves the saved .tif and velocity fields unmirrored, so the
  data still means what the camera actually saw.  The test-suite asserts that
  '-u' on the raw image and 'u' on the flipped image give the identical
  feedback value.

  Use a flip when you want the IMAGE ITSELF mirrored — typically so the live
  display reads left-to-right and matches how you think about the facility,
  or to match an earlier data set.  That is a presentation choice, and it is
  a perfectly good reason; just set the ROIs in the flipped frame.

  Note also the Release 4.0 limitation, unchanged: flip_state is a per-run
  guard, so re-processing .tif files that already had the flip baked in
  during an earlier run will flip them a second time.


--------------------------------------------------------------------------------
  4. THE FEEDBACK VELOCITY
--------------------------------------------------------------------------------

    U_control_raw = statistic( component(U,V) over VALID nodes in ControlROI )
                    * velocity_scale

  component     'u'  = +U   (jet left -> right; the shipped default)
                '-u' = -U
                'v'  = +V   (V is positive DOWNWARD in this codebase)
                '-v' = -V   (an upward jet)
                'magnitude'  available but NOT recommended for a jet: it is
                             positive-definite, cannot distinguish forward
                             from reverse flow, and biases high in noise.

  statistic     'mean' (default) or 'median'.

  A node is VALID when all of these hold:
      - U and V are finite;
      - it passed Westerweel-Scarano outlier detection (the mask, not the
        substituted value);
      - its normalised correlation coefficient >= min_correlation, when
        use_correlation_gate is on;
      - |U|,|V| <= max_abs_displacement_px, when that is set.

  The measurement is declared INVALID, and never reaches the PID, when
      n_valid < max(min_valid_vectors, ceil(min_valid_fraction * n_total)).

TERMINOLOGY.  This is a CONTROL-REGION velocity estimate.  If the ControlROI
sits on the jet core it is a core velocity — it is NOT the cross-sectional
bulk velocity and NOT the nozzle exit velocity.  The variable is called
U_control everywhere in the code and the logs for exactly that reason.
Displaying it as "Uj" is a labelling convenience; the definition above is what
it actually is.

UNITS.  U_control is computed in px/frame and converted ONCE, at the
measurement, so the whole loop stays internally consistent in whatever unit
you choose.  There are two ways to set it.

  Working in m/s (recommended).  Set the optical resolution you read off a
  calibration target:

      CALIBRATION_PX_PER_MM = 20.0        # px/mm
      PULSE_SEPARATION_S    = None        # None -> derived, see below

  and the set-point, the measurement, the PID gains, the output limits, the
  logs, the plots and the HUD are all in m/s.  The conversion is

      U [m/s] = U [px/pulse] / CALIBRATION_PX_PER_MM * 1e-3 / dt

  dt is the separation between the two correlated pseudo-frames.  Leaving
  PULSE_SEPARATION_S = None derives it from the acquisition: consecutive
  pseudo-frames are one accumulation window apart, so dt = 1/f_acq — which is
  exactly 1/f_laser when the laser fires once per pseudo-frame, i.e. when
  LASER_FREQUENCY_HZ == f_acq.  Set it explicitly only if that is not true,
  for example with pulse-pair illumination.  If LASER_FREQUENCY_HZ and f_acq
  disagree, start-up says so, because then one of the two is misconfigured.

  Working in px/frame.  Leave CALIBRATION_PX_PER_MM = None.  Nothing is
  assumed about the optics at all.

Start-up prints the resolved conversion both ways, for example at 20 px/mm
and 500 Hz:

      frame separation dt : 2000.0 us (500.00 Hz)  [accumulation window]
      resolution          : 20 px/mm
      1 px/frame          = 0.025 m/s
      1 m/s               = 40 px/frame

WATCH THE GAINS.  The PID gains are in volts per (velocity unit), so changing
units rescales them: at 40 px/frame per m/s, a controller tuned in px/frame
needs gains 40x larger to mean the same thing in m/s.  Start-up prints that
factor.  Tune in the unit you intend to run in.

WATCH THE DYNAMIC RANGE.  A set-point in m/s implies a displacement in px,
and the correlation can only measure so much.  Start-up converts the peak
set-point to px/frame and compares it against the interrogation window:

Since  displacement [px] = U * dt * (px per metre),  a LONGER dt (lower f_acq)
gives a LARGER pixel displacement, and a shorter dt a smaller one:

    > window_size/2   the correlation WRAPS. It cannot be measured at all and
                      the loop will chase noise. Start-up flags this loudly
                      and names the f_acq that would fix it. Shorten dt (RAISE
                      f_acq), enlarge window_size, or reduce the magnification.
    > window_size/4   beyond the usual PIV rule of thumb; correlation quality
                      degrades. Check the CC column. Start-up suggests an
                      f_acq that brings it back.
    < 0.5 px/frame    sub-pixel noise dominates the feedback signal. Lengthen
                      dt (LOWER f_acq) or increase the magnification.

  At 20 px/mm, 500 Hz and window_size = 48, the usable band is roughly
  0.0125 to 0.3 m/s, with 0.3 m/s already at the quarter-window limit.  Check
  this against your intended operating range BEFORE the first run; it may
  drive your choice of f_acq, magnification or window size.


--------------------------------------------------------------------------------
  5. TEMPORAL FILTER
--------------------------------------------------------------------------------

  'none'  U_control_filtered == U_control_raw.
  'ma'    Moving average over the last `window` VALID samples.
          Group delay ~ (window-1)/2 samples.
  'ema'   First-order low-pass.  alpha = dt/(tau+dt) is recomputed from the
          MEASURED dt every update, so the corner stays at 1/(2*pi*tau) even
          when the loop jitters.  Group delay ~ tau seconds.

Both U_control_raw and U_control_filtered are kept, logged and plotted.  The
PID uses the filtered value.

Filtering is not free.  A moving average of length N at control rate f_c adds
about (N-1)/(2*f_c) seconds of phase lag directly into your loop.  The filter
kind and its length are printed in the run header and written into every log,
so the delay you chose is never invisible.  The test-suite measures the
group delay of a length-21 moving average and asserts it is (N-1)/2 samples.

Dropouts do not corrupt the filter: only valid samples are fed in, so a bad
field neither injects a zero nor advances the memory.


--------------------------------------------------------------------------------
  6. RUNNING IT
--------------------------------------------------------------------------------

6.1  EBIV only — Release 4.0 behaviour

     FLAG_STREAM = True ;  RUN_MODE = 'ebiv'

     No pump backend is created and no voltage is ever issued.  Set
     PIV_SUBPIXEL = False to reproduce Release 4.0's real-time output
     bit-for-bit (the test-suite asserts this).

6.2  Manual / open-loop pump control

     FLAG_STREAM = True ;  RUN_MODE = 'manual'

     rtEBIV keeps measuring; [+] and [-] step the voltage by
     CAL_MANUAL_STEP_V, [0] returns to the safe voltage.  Everything is
     logged.  Use this to find the operating range before automating it.

6.3  Open-loop calibration  — DO THIS BEFORE TUNING

     FLAG_STREAM = True ;  RUN_MODE = 'calibration'
     CAL_MODE = 'steps'   (or 'sweep')

     'steps' holds each of CAL_VOLTAGES for CAL_DWELL_S; the first
     CAL_SETTLE_S of each dwell is marked as transient so you can separate the
     static curve from the response.  'sweep' ramps v_start -> v_stop over
     CAL_SWEEP_DURATION_S and optionally back, which exposes hysteresis.

     Logged per control step: timestamp, commanded voltage, U_control_raw,
     U_control_filtered, n_valid / n_total, controller state.  From this you
     get both the static map V -> U_control and the transient response
     (time constant, dead-band, transport delay) that the gains must be based
     on.  Nothing in the software presumes the shape of that map.

6.4  Closed loop

     FLAG_STREAM = True ;  RUN_MODE = 'closed_loop'

     Starts in MANUAL.  Bring the jet to a sensible operating point with
     [+]/[-], wait until the HUD shows a stable U_ctrl_flt and a healthy
     valid-vector count, then press [c].  Arming is bumpless: the PID's
     integral is preloaded so its first output equals the voltage the pump is
     already receiving.  [c] again disarms, holding the present voltage.
     [x] forces the SAFE state at any time.

     Arming is refused if there is no valid velocity measurement yet.

     WHAT [+] AND [-] DO depends on whether the loop is closed, because that
     decides what is actually yours to command:

       loop OPEN (MANUAL or SAFE)
           the PUMP VOLTAGE, in steps of CAL_MANUAL_STEP_V.  There is no
           target yet, so the voltage is the only thing to move.

       loop CLOSED (or HOLD) with REFERENCE_KIND = 'live'
           the TARGET VELOCITY, in steps of REF_LIVE_STEP, clamped to
           [REF_LIVE_MIN, REF_LIVE_MAX].  The PID owns the voltage; you say
           how fast the jet should go and it works out the rest.  This is the
           point of closing the loop: you command the physical quantity, not
           the actuator.

       loop CLOSED with any other REFERENCE_KIND
           nothing, and the log says so.  The target is following its own
           trajectory (step, sine, file, random) and letting a key press
           silently override it would corrupt the run.  Disarm with [c] if
           you want the voltage back.

     Every press logs which of the two moved, and the HUD carries a
     "live target" line whenever the reference is operator-driven.

     [t] snaps the live target onto the current filtered velocity.  Press it
     just before [c] and the loop closes with zero initial error, so the only
     thing that then moves the jet is your own [+]/[-].

     'live' is the interactive counterpart of RUN_MODE = 'manual'.  They are
     not the same thing and it is worth being clear which you want:

         RUN_MODE 'manual'                 REFERENCE_KIND 'live'
         no controller                     PID running
         [+]/[-] set the pump voltage      [+]/[-] set the target velocity
         the jet does what the pump does   the jet is held at what you asked
         use it for calibration            use it for an experiment

6.5  No hardware at all

     FLAG_SELFTEST = True        run the 104-check test-suite
     FLAG_SIMULATE = True        closed loop against a simulated plant,
                                 writes simulation_output/*.png
     python bench_release5.py    CPU benchmark on your machine

     The whole control law, logger, ROI selection and visualisation run with
     no camera and no Analog Discovery.  ebiv_control.py has no module-level
     dependency on ebiv_hardware.py, and the test-suite asserts that.

--------------------------------------------------------------------------------
  6b. THE GPU PATH   (restored and fixed in Release 5.2)
--------------------------------------------------------------------------------

  PIV_USE_GPU = True            (or the "GPU correlation" tick on PIV & ROIs)

  Needs torch built with CUDA.  Without it the run falls back to the CPU and
  says so, so leaving the flag on is harmless.  torch is installed PER
  INTERPRETER: if check_gpu.py says it is missing, check WHICH python it
  printed before concluding anything about the machine.

  WHAT IT COVERS

    Live stream, including closed loop    yes
    Offline pyramidal PIV                 yes

  HOW IT PARALLELISES

    All the interrogation windows of ONE snapshot, together.  torch.unfold
    turns the frame into an (N, ws, ws) batch where N = grid_y * grid_x, and
    one batched rfft2/irfft2 covers the lot.  Snapshots are still processed
    one after another, so the speed-up scales with N: a large DisplayROI with
    a small node distance gives the GPU real work.

  IS IT SAFE FOR THE CLOSED LOOP?

    For CORRECTNESS, yes, and this was not true before Release 5.2.

    Release 4.0's real-time GPU kernel (batch_cross_correlate) returns the
    INTEGER peak and no CC, because Release 4.0's CPU path did the same and
    there was no controller to feed.  Release 5 needs both: sub-pixel because
    a 1 px quantisation on a 5 px displacement is a 20% quantisation of the
    feedback signal, and CC because the ControlROI validity gate is what
    decides whether a measurement may reach the PID at all.

    Release 5.2 adds GPUCorrelator.correlate(), which returns (U, V, CC) with
    sub-pixel, exactly like CPUCorrelator.  Measured against it: identical
    integer peaks, ~3e-6 px on the sub-pixel displacement, ~3e-6 relative on
    CC, in both 2-frame and triple-correlation mode.  The estimator and the
    PID cannot tell which backend produced the numbers.

    For LATENCY, unknown, and this is the part to be careful about.  A GPU
    buys THROUGHPUT; a control loop cares about the delay from photons to
    voltage and about how much that delay varies.  The host-device round trip
    adds both, and Release 4.0's own report measured 1.71 ms just to upload
    three frames.  Before trusting PID gains tuned on the GPU, run the same
    configuration on both backends and compare the latency summary printed at
    the end of the run.  Nothing here claims the GPU is faster for the loop.

  DO NOT EXPECT RELEASE 4.0's SPEED-UP NUMBER

    That report measured a kernel doing neither sub-pixel nor CC.  Both are
    real extra work.  The 14.4x on the correlation stage does not carry over
    to correlate(); measure it on your own hardware.

  BEFORE YOU TRUST A GPU RESULT

        python tools/check_gpu.py

    Runs the real offline PIV on both backends over the same synthetic frames
    with a known displacement and compares them.  Release 4.0's offline path
    was wrong twice (audit B7, B8) - and, on the evidence, was never actually
    run, because B7 raises on the first snapshot.  Both are fixed in 5.2, but
    the fix was verified on CPU tensors because the machine that wrote it has
    no CUDA.  This closes that gap on YOUR hardware, and it detects each of
    the historical bugs if they are ever reintroduced.

  CAVEAT: on the OFFLINE pyramidal path CC is not computed and is saved as
  NaN.  The live path does compute it.


--------------------------------------------------------------------------------
  7. ANALOG DISCOVERY 3: CHANNEL ALLOCATION AND API CALLS
--------------------------------------------------------------------------------

7.1  Allocation (defaults)

     Analog Out ch0  (W1)  laser trigger, continuous square wave
     Analog Out ch1  (W2)  pump command, DC, 0..5 V
     Analog In  ch0  (1+)  optional, only for the self-check in §8

     The AD3 has two ±5 V arbitrary-waveform outputs and 16 DIO lines, so
     0-5 V on W2 is comfortably inside the hardware range.

     If your laser is driven from a DIO pin instead, set
     LASER_BACKEND = 'pattern' and LASER_DIO_CHANNEL.  DigitalOut is a
     physically separate instrument from AnalogOut, so pump updates cannot
     reach it at all; the pump then takes Analog Out ch0.

     LASER_BACKEND = 'external' tells Release 5.0 not to generate the laser
     at all.  Use it only if something other than this AD3 is driving it.

7.2  Exactly what is called

     Once, at start-up:

       FDwfEnum, FDwfDeviceOpen(device_index, &hdwf)
       FDwfDeviceAutoConfigureSet(hdwf, 0)
             AutoConfigure OFF, so no Set call silently reconfigures the
             device.  Every hardware update is an explicit, channel-specific
             Configure.

       laser, on channel L:
         FDwfAnalogOutNodeEnableSet   (hdwf, L, Carrier, 1)
         FDwfAnalogOutNodeFunctionSet (hdwf, L, Carrier, funcSquare)
         FDwfAnalogOutNodeFrequencySet(hdwf, L, Carrier, laser_frequency_hz)
         FDwfAnalogOutNodeAmplitudeSet(hdwf, L, Carrier, laser_amplitude_v)
         FDwfAnalogOutNodeOffsetSet   (hdwf, L, Carrier, laser_offset_v)
         FDwfAnalogOutNodeSymmetrySet (hdwf, L, Carrier, laser_duty_percent)
         FDwfAnalogOutRunSet          (hdwf, L, 0)      infinite
         FDwfAnalogOutRepeatSet       (hdwf, L, 0)      infinite
         FDwfAnalogOutIdleSet         (hdwf, L, ...)
         FDwfAnalogOutConfigure       (hdwf, L, 1)      START this channel

       pump, on channel P:
         FDwfAnalogOutNodeEnableSet   (hdwf, P, Carrier, 1)
         FDwfAnalogOutNodeFunctionSet (hdwf, P, Carrier, funcDC)
         FDwfAnalogOutNodeAmplitudeSet(hdwf, P, Carrier, 0.0)
         FDwfAnalogOutNodeOffsetSet   (hdwf, P, Carrier, startup_voltage)
         FDwfAnalogOutRunSet          (hdwf, P, 0)
         FDwfAnalogOutRepeatSet       (hdwf, P, 0)
         FDwfAnalogOutConfigure       (hdwf, P, 1)      START this channel
         FDwfAnalogOutConfigure       (hdwf, P, 3)      priming apply, see below

     Per control step, and NOTHING else:

         FDwfAnalogOutNodeOffsetSet   (hdwf, P, Carrier, V)
         FDwfAnalogOutConfigure       (hdwf, P, 3)

     fStart = 3 is documented in the WaveForms SDK reference manual as
     "apply the configuration dynamically without changing the state of the
     instrument".  The channel index is always explicit.

     The pump channel uses funcDC with amplitude 0, so the output is entirely
     determined by the node OFFSET; that is why a voltage change is a single
     OffsetSet.

7.3  What is deliberately NEVER done

       * FDwfAnalogOutConfigure(hdwf, -1, ...)   -1 means "every enabled
         Analog Out channel" and would address the laser.  Not used anywhere.
       * FDwfAnalogOutReset / FDwfDeviceReset after start-up.
       * Reopening or re-enumerating the device.  One handle for the session.
       * Stopping or restarting the laser channel.  After start_laser()
         returns, no function in ebiv_hardware.py addresses that channel
         again, and the verification mode reports the count so you can check.

7.4  The priming apply

     A Digilent forum report ("AD3: first FDwfAnalogOutConfigure(ch, 3) glitch
     observed after channel start") indicates that the FIRST dynamic apply
     after a channel start can disturb the output.  Release 5.0 issues that
     first apply during pump initialisation, at the startup voltage, before
     any control action — so if the effect is real it lands at a harmless
     moment rather than on the first control step.  Watch for it anyway in §8.

7.5  Electrical notes, offered as cautions rather than advice

     * The EcoDrift 4.3 auxiliary input accepts 0-10 V; we command only 0-5 V,
       which is what the previous VKI setup used (an Arduino PWM pin, limited
       to 5 V).  The AD3 gives a true DC level rather than a PWM average, so
       there is no ripple for the pump input to filter.
     * The AD3 output and the pump control input must share a ground
       reference.  Check this before connecting anything.
     * Verify the AD3's output drive is adequate for the pump input's load.
       If in doubt, buffer it.
     * This is water and mains-powered equipment. Ground loops and splashes
       are your problem, not the software's.


--------------------------------------------------------------------------------
  8. HARDWARE VERIFICATION: DOES A PUMP UPDATE DISTURB THE LASER?
--------------------------------------------------------------------------------

Do this once, before any closed-loop run, after any change to the AD3 wiring
or the WaveForms version.

  1.  Close the WaveForms desktop application.
  2.  In EBIV_Main.py set FLAG_VERIFY_HARDWARE = True and AD3_ENABLED = True.
      Set the LASER_* parameters to your real laser settings.
  3.  Put an oscilloscope on the laser output (W1, or the DIO pin).
      Trigger on its rising edge.  Enable frequency, pulse-width and duty
      measurements, and turn on trigger-stability / jitter measurement or
      persistence display.
  4.  Run:   python EBIV_Main.py
      Press ENTER when the scope is stable.
  5.  The routine steps the pump through 0, 1, 2, 3, 4, 5 V, holding each for
      a few seconds and printing a banner at each step so you can correlate
      the trace with the commanded voltage.
  6.  At every step confirm on the SCOPE that these do not change:
          - laser frequency
          - pulse width
          - duty cycle
          - trigger stability / jitter (persistence should not smear)
          - amplitude and offset
      Also watch for any momentary dropout at the instant of the change.
  7.  The routine then prints:
          - the number of laser-channel configuration calls made during the
            sweep.  This must be 0.
          - the number of pump updates, failures, and the per-update time.
          - a statement that the device was opened once and never reset.

  Optional automated self-check.  Wire the laser output back into scope input
  1+ and set use_internal_scope=True in the FLAG_VERIFY_HARDWARE call.  The
  AD3 then digitises its own laser waveform before and after each pump change
  and reports frequency drift in ppm, pulse-width drift in microseconds, duty
  cycle and period jitter.  This is a convenient regression check, but be
  clear about its limitation: the generator and the digitiser are in the same
  device and share a reference clock, so it is blind to a common clock
  disturbance and its jitter figure is a lower bound.  It does not replace the
  external scope.

  If anything DOES change: do not proceed to closed-loop operation.  Try
  LASER_BACKEND = 'pattern', which moves the laser to the Pattern Generator —
  a separate instrument from Analog Out, so an Analog Out apply cannot reach
  it.  Then repeat this procedure.


--------------------------------------------------------------------------------
  9. MISSING OR BAD MEASUREMENTS
--------------------------------------------------------------------------------

A measurement is rejected when any of these is true:

    - fewer than max(min_valid_vectors, min_valid_fraction * n_total) valid
      vectors in the ControlROI;
    - the value is NaN or Inf (checked twice: in the estimator and again in
      the supervisor);
    - the measurement is older than max_measurement_age_s;
    - its sequence number has not advanced since the last control step, i.e.
      no new field arrived (this is what catches a stalled camera or a stalled
      PIV worker);
    - the PIV worker raised, in which case it publishes an explicitly invalid
      measurement rather than dying.

Response, in order:

    < hold_timeout_s          HOLD.  The last commanded voltage is maintained.
                              The PID does not integrate and its derivative
                              state is cleared, so no phantom error builds up
                              against data that does not exist.  This covers
                              the ordinary case of a few bad EBIV frames.

    > safe_timeout_s          SAFE.  The pump is driven to safe_pump_voltage
                              and the loop DISARMS.  Recovery requires an
                              explicit operator re-arm, so a flapping
                              measurement can never silently re-engage the
                              controller.

Every state change is logged once, at the transition, to both the console and
<run>_events.csv.  Counters for valid / hold / stale / invalid / safe steps
appear in the periodic summary and in the final report.

On shutdown — normal quit, unhandled exception, or Ctrl-C — the pump is driven
to safe_pump_voltage before the device is closed.  That path is in a `finally`
block, so it runs even if the acquisition loop throws.

--------------------------------------------------------------------------------
  11b. WHAT THE LIVE WINDOWS SHOW
--------------------------------------------------------------------------------

Two windows, refreshed independently and neither able to affect control
timing (visualization_rate_hz and plot_rate_hz).

MAIN IMAGE WINDOW
  * the pseudo-frame, or a black background with [b];
  * velocity vectors over the DisplayROI, coloured by magnitude;
  * the DisplayROI outline, labelled at its bottom-left;
  * the ControlROI as a cyan rectangle with corner ticks, labelled at its
    bottom-right, so what the controller is looking at is never in doubt;
  * a status panel, top-left, on a translucent background so it stays
    readable over the vector field:

        [CLOSED_LOOP]              state, colour-coded
        U_target      0.142 m/s    the set-point
        U_ctrl_flt    0.140 m/s    what the PID is acting on
        U_ctrl_raw    0.145 m/s    before the temporal filter
        V_pump        2.317 V      what went to the pump
        valid         52/56 (92.9%)  green above min_valid_fraction, amber below
        ! reason                   only when the measurement is rejected

STRIP CHART  ("EBIV Control — time history", toggle with [g])
  Top pane, velocity: U_target (green), U_control_filtered (blue),
  U_control_raw (faint red).  Bottom pane: the pump command.  Both panes have
  gridlines with labelled ticks, and the latest value of each trace is printed
  at the right-hand edge.

  Three details that matter when reading it live:

  * The pump pane AUTOSCALES to what the pump is actually doing, with the
    configured limits shown in its title and a dashed line at the ceiling when
    it is in view.  Pinned to the full 0-5 V range, a realistic 0.9-1.1 V
    trace occupies 4% of the pane height and tells you nothing; autoscaled it
    fills about two thirds of it.
  * The velocity pane takes its limits from the 1st/99th percentile of the
    raw trace but always shows the target and the filtered trace in full, so a
    single bad frame cannot compress the plot and the set-point can never
    scroll out of view.
  * While the measurement is invalid the filtered trace HOLDS its last value —
    correct behaviour, but it looks like live flow.  Those stretches are drawn
    DIMMED, and the controller state is shown as a coloured band along the
    bottom of the velocity pane (amber HOLD, red SAFE, grey MANUAL) and next
    to the clock.  A held number never looks like a measured one.

  In manual and calibration mode there is no set-point, so the target trace is
  absent and the chart shows the measured velocity against the commanded
  voltage — which is exactly the picture you want while stepping the pump to
  build the V -> U curve.

       limit, and refusal of a ControlROI outside the DisplayROI.
    3  Filters: MA arithmetic, EMA step response to 1-1/e at tau, rate
       independence, the measured group delay of a length-21 MA, refusal of
       non-finite input.
    4  PID: P/I arithmetic, both saturation limits, clamp and back-calculation
       anti-windup (with a no-anti-windup control case that DOES wind up),
       slew limiting, derivative-on-measurement removing set-point kick,
       derivative filtering attenuating noise, bumpless transfer, dt clamping,
       and 4000 adversarial steps that never leave [v_min, v_max].
    5  Invalid measurements: HOLD freezes the output, recovery returns to
       CLOSED_LOOP, a long dropout escalates to SAFE, SAFE latches, NaN/Inf
       never produce a NaN command, stale-but-valid is rejected on age, and a
       frozen sequence number is treated as no new data.
    6  Reference generators: all five kinds, seed reproducibility, band
       limiting demonstrated against white noise, clipping, and a check that
       the generators do not reference the PID.
    7  Closed loop against the simulated plant: the plant is confirmed
       non-linear; step and sine tracking; a zero-gain control run showing the
       tracking is due to feedback; noise plus dropouts; a long dropout
       reaching SAFE; an unreachable set-point saturating without windup.
    8  Hardware abstraction: mock pump limits, channel-clash refusal, config
       cross-checks, the laser pulse-metric function, and a check that the
       control law does not import the hardware layer.
    9  Config validation and the logger's five output files.
   10  Visualisation renders, tolerates NaN, and is fast.
   11  Session and GUI: preset round-trip and tolerance of unknown keys,
       the directory layout, the offline chain running the right steps in the
       right order, streaming dispatch, and that EBIV_Main hands the GUI a
       valid session.
   12  Analog Discovery call sequence (test_hardware_mock.py): the real
       AnalogDiscovery3 and AnalogOutPump are run against a fake WaveForms
       runtime that records every ctypes call, and the recording is asserted
       against the design claims — device opened once, AutoConfigure off, the
       laser channel never addressed after start-up (checked across 200 pump
       updates and a closed-loop run), idxChannel never -1, no reset, each

   13  Integration (test_integration.py): the REAL stream_camera() is run

       shutdown.

--------------------------------------------------------------------------------
  14. KNOWN LIMITATIONS AND NEXT STEPS
--------------------------------------------------------------------------------

Limitations

  * No gains are supplied.  PID_KP/KI/KD ship at zero because there is no
    calibration yet and inventing gains would be worse than useless.
  * The pump/jet model in simulate_control.py is a toy.  It is non-linear on
    purpose, but it is not the EcoDrift 4.3.
  * Performance numbers in AUDIT_R4_to_R5.md come from a shared 2-core cloud
    container and vary by up to 50% between runs there.  The per-stage gains
    (2-4x on window extraction and cross-power) are structural and should
    hold; the end-to-end figure depends on your ROI and memory bandwidth.
  * Laser/pump independence is argued from the SDK semantics and the code
    structure, and is NOT yet demonstrated on this hardware.  §8 is how you
    demonstrate it.
  * The GPU backend is unused and carries two unfixed bugs (B7, B8).  Do not
    enable it.
  * The controller acts on one scalar.  No spatial or multi-input control.
  * The camera's own trigger path is unchanged from Release 4.0: Release 5.0
    generates the laser waveform but does not close the loop between the
    generated waveform and the camera's trigger-in.  If you want hardware
    phase locking rather than 'auto' phase detection, wire the AD3 laser
    signal to the camera trigger input and use trigger_mode='external'.
  * Threading, not multiprocessing.  Justified by measurement (the FFT
    releases the GIL) but it does mean a single CPython process.
  * The strip chart is deliberately simple. It is not a substitute for
    analysing the logged CSV afterwards.

Recommended next steps, in order

  1.  §8 hardware verification with a scope. Do not skip it.
  2.  RUN_MODE='calibration', CAL_MODE='steps', over the range you intend to
      use.  Extract the static curve V -> U_control and the step response.
      Expect a dead-band at low voltage and a non-linear curve.
  3.  From the step response take the apparent time constant tau and delay L.
      Choose CONTROL_RATE_HZ around 10-20x the closed-loop bandwidth you
      expect, not around the camera rate.  Set FILTER_TAU_S well below tau so
      the filter is not the dominant lag.
  4.  Tune Kp first with Ki = Kd = 0 at a mid-range operating point.  Add Ki
      to remove steady-state error.  Add Kd only if the derivative is not
      dominated by measurement noise — check the d_term column in the log.
      Because the plant is non-linear, gains tuned at one operating point will
      not be optimal at another; consider gain scheduling on V, or inverting
      the measured static curve as a feed-forward term and letting the PID
      handle only the residual.
  5.  Verify HOLD and SAFE on the real rig before a long run: block the laser
      briefly, and confirm the controller holds and then goes safe.
  6.  Only then consider GPU acceleration, and fix B7/B8 first.
